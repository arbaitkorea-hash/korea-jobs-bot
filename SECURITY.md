# Аудит безопасности — JST ART

Итоговый отчёт по 12 пунктам из технического задания. Статус на каждый пункт: что
проверено, что реализовано, что осталось на усмотрение владельца при деплое.

## 1. Аутентификация админки

- Пароли хешируются **bcrypt** (12 раундов) — `src/auth.ts`, `prisma/seed.ts`.
- Rate limiting на попытки входа: 10 попыток / 10 минут на IP (`src/lib/rate-limit.ts`,
  используется внутри `authorize()` в `src/auth.ts`).
- Блокировка аккаунта: после 5 неверных паролей аккаунт блокируется на 15 минут
  (`AdminUser.failedLoginAttempts` / `lockedUntil` в схеме Prisma).
- Постоянное время ответа при несуществующем email (фиктивный `bcrypt.compare`),
  чтобы не давать различать "нет такого email" и "неверный пароль" по таймингу.
- Cookies сессии: `httpOnly: true`, `sameSite: "lax"`, `secure: true` в продакшене
  (`src/auth.ts`, блок `cookies.sessionToken`).
- CSRF на форме входа: обеспечивается встроенным механизмом NextAuth (double-submit
  CSRF-токен на `/api/auth/callback/credentials`).
- **Осталось на усмотрение**: 2FA (в схеме Prisma уже есть поля `twoFactorSecret` /
  `twoFactorEnabled`, но TOTP-флоу не реализован в MVP — добавляется без миграции схемы).

## 2. Авторизация

- Все `/admin/*` защищены на уровне `src/proxy.ts` (Next.js 16 "proxy", аналог
  middleware, работает в Node.js runtime — поэтому может напрямую использовать
  `auth()` с Prisma/bcrypt без edge-ограничений).
- Дополнительно — серверная проверка сессии в `src/app/admin/(dashboard)/layout.tsx`:
  UI не единственная защита, при прямом заходе в обход прокси всё равно редиректит.
- Все мутирующие server actions (`saveArtwork`, `deleteArtwork`, `reorderArtworks`,
  `saveCollection`, `saveBlogPost`, `updateOrderStatus` и т.д.) начинаются с
  `await auth()` / `requireSession()` — проверка на сервере, не только скрытие кнопок.
- `/api/admin/upload` — та же проверка сессии + explicit same-origin check (см. п. 7/CSRF).

## 3. Валидация ввода

- Все формы валидируются на сервере через **Zod** (`src/lib/validation.ts`):
  контакты, заказы, картины, коллекции, статьи блога, логин.
- Клиенту не доверяем данные о цене: `/api/orders` пересчитывает сумму заказа из
  актуальных цен в БД по `artworkId`, а не из тела запроса (`src/app/api/orders/route.ts`).
- Публикация картины без `altText` или без изображения блокируется на сервере
  (`saveArtwork`), а не только визуальной подсказкой в форме.

## 4. SQL-инъекции

- Везде используется Prisma Client с параметризованными запросами.
- `$queryRaw`/`$executeRaw` **не используются нигде в коде приложения** (проверено
  `grep` по `src/` и `prisma/` — совпадения есть только внутри самого сгенерированного
  клиента Prisma, это его типовые определения, не наш код).

## 5. XSS

- React по умолчанию экранирует весь текстовый контент — `dangerouslySetInnerHTML`
  использован только в двух местах:
  1. **JSON-LD** (`src/components/seo/json-ld.tsx`) — данные из БД, но на всякий
     случай экранируем `<` в `<`, чтобы значение поля не могло преждевременно
     закрыть `<script>` и внедрить код.
  2. **HTML блога** — санитизируется **DOMPurify** дважды: при сохранении в
     `saveBlogPost` (`src/app/admin/(dashboard)/blog/actions.ts`) и повторно при
     рендере на публичной странице (`src/app/(site)/blog/[slug]/page.tsx`) — вторая
     линия защиты, если в БД когда-либо попадёт не до конца очищенный HTML.
- WYSIWYG-редактор — `contentEditable`, не источник истины по безопасности сам по
  себе; весь HTML проходит через DOMPurify перед сохранением.

## 6. Загрузка файлов

- Реальный формат файла проверяется декодированием через **sharp** (magic bytes),
  а не по `Content-Type` или расширению — подделать заголовок недостаточно
  (`src/lib/storage.ts`, `saveImage()`).
- Ограничение размера — 10 МБ.
- Имена файлов — `crypto.randomUUID()`, пользовательское имя файла нигде не
  используется как часть пути (защита от path traversal).
- Файлы хранятся в `storage/uploads/` — вне `public/`, отдаются только через
  `/api/media/[filename]` со строгой regex-валидацией имени
  (`^[0-9a-f-]{36}-(full|thumb)\.webp$`) и фиксированным `Content-Type: image/webp`.
- Эндпоинт загрузки — только для авторизованных (`session.user`), с rate limit
  (30 загрузок / 10 минут) и explicit same-origin проверкой (см. ниже).
- **Осталось на усмотрение**: на Vercel файловая система эфемерна и доступна на
  запись только в `/tmp` — для продакшена нужно подключить внешнее S3-совместимое
  хранилище (Supabase Storage или Cloudinary, у обоих есть бесплатный тариф) и
  переопределить `saveImage()` в `src/lib/storage.ts`, не меняя остальной код.

## 7. Заголовки безопасности и CSRF

Заданы в `src/proxy.ts` для всех ответов:

- `Content-Security-Policy`
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy: camera=(), microphone=(), geolocation=()`
- `Strict-Transport-Security` (только в проде)

**Осознанный компромисс в CSP**: `script-src 'self' 'unsafe-inline'` вместо
nonce-based CSP. Next.js App Router вставляет инлайн-скрипты для стриминга RSC
(`self.__next_f.push(...)`), которым нужен либо nonce, либо `'unsafe-inline'`.
Строгий nonce-подход официально описан в доках Next.js, но требует читать
`headers()` в layout — а это переводит **все** страницы в динамический рендеринг,
что ломает SSG/ISR для галереи и блога (ключевое SEO-требование ТЗ). Мы выбрали
`'unsafe-inline'` для `script-src`, сохранив статическую генерацию. Остаточный риск
закрыт другими слоями: автоэкранирование React, DOMPurify на блоге (дважды),
экранирование JSON-LD, отсутствие пользовательского `eval`/`innerHTML` где-либо ещё.
`style-src 'self' 'unsafe-inline'` — аналогичный компромисс из-за инлайн-стилей
Tailwind/next/image; риск там ниже (инлайн-стили не исполняют JS).

**CSRF на API-роутах**:
- `/api/orders`, `/api/contact` — принимают только `application/json`, что требует
  CORS preflight для кросс-доменных запросов; простая HTML-форма с чужого домена
  не может отправить такой запрос без явного разрешения с нашей стороны — встроенная
  защита форматом данных.
- `/api/admin/upload` — принимает `multipart/form-data`, это "simple request" по
  правилам CORS: браузер отправит его кросс-доменно вместе с cookie сессии без
  preflight. Добавлена явная проверка `Origin` (`src/lib/same-origin.ts`).
- Server actions (`"use server"`) — защищены встроенной same-origin проверкой
  Next.js автоматически, без дополнительного кода.
- Форма входа — CSRF-токен NextAuth (double-submit cookie).

## 8. Секреты

- Все ключи — в `.env` (не в репозитории, см. `.gitignore`: `.env*`).
- `.env.example` добавлен с описанием каждой переменной, без реальных значений.
- Проверено `grep` по `src/` — захардкоженных паролей/ключей в коде нет.

## 9. Rate limiting

Реализован in-memory token bucket (`src/lib/rate-limit.ts`), применяется на:
- Вход в админку — 10 попыток / 10 мин / IP.
- `/api/contact` — 5 запросов / 10 мин / IP.
- `/api/orders` — 5 запросов / 10 мин / IP.
- `/api/admin/upload` — 30 запросов / 10 мин / IP.

Плюс honeypot-поле (`website`) на формах контактов и заказа — скрытое от людей CSS,
боты его заполняют и получают тихий "успех" без записи в БД.

**Ограничение**: состояние лимитера — в памяти процесса, не общее между
инстансами serverless-функций. Это best-effort защита, не строгая гарантия на
многоинстансном проде. Для строгого лимита — бесплатный тариф Upstash Redis
(`@upstash/ratelimit`), меняется без изменения вызывающего кода.

## 10. Зависимости

`npm audit` (и с `--production`, и полный) — **0 уязвимостей** на момент сборки.
Рекомендация: включить Dependabot/`npm audit` в CI, чтобы отслеживать появление
новых уязвимостей после деплоя.

## 11. HTTPS

- CSP включает `upgrade-insecure-requests`.
- `Strict-Transport-Security` выставляется в проде (`src/proxy.ts`).
- Редирект HTTP → HTTPS не реализован в коде приложения намеренно: при деплое на
  Vercel это делает граница платформы автоматически до того, как запрос дойдёт до
  Next.js — дублировать редирект в приложении избыточно и может создать петлю за
  обратным прокси. **Проверить при деплое**: в настройках домена на Vercel HTTPS
  включён по умолчанию, ничего дополнительно делать не нужно.

## 12. Резервное копирование

Рекомендации (не входит в код приложения — операционная процедура):
- **БД**: и Supabase, и Neon включают автоматические point-in-time backups на
  платных тарифах; на бесплатном — настроить `pg_dump` по расписанию (например,
  через GitHub Actions cron) в объектное хранилище.
- **Медиа**: как только загрузка картин переведена на внешнее S3-совместимое
  хранилище (см. п. 6), включить версионирование бакета — это и есть бэкап.
  Пока используется локальный `storage/uploads` (только dev) — бэкапить не нужно,
  это не прод-хранилище.
- **Код**: репозиторий на GitHub — это уже бэкап кода, при условии регулярных push.
