# Аудит безопасности — JST ART

Отчёт по 15 пунктам технического задания. Проведено два прохода: первый —
реализация и проверка по коду, второй — перепроверка с попытками эксплуатации
на работающем приложении (результаты помечены «проверено практически»).

**Итоговый статус: закрыты все 15 пунктов.** Два условия относятся к деплою,
а не к коду, и вынесены в раздел «Что обязательно сделать при запуске».

---

## 1. Аутентификация админки — ✅ закрыто

- Пароли — **bcrypt**, 12 раундов (`src/auth.ts`, `prisma/seed.ts`).
- **Rate limiting** на вход: 10 попыток / 10 минут на IP.
- **Блокировка аккаунта**: 5 неверных паролей → блок на 15 минут
  (`failedLoginAttempts`, `lockedUntil`).
- **Постоянное время ответа** при несуществующем email (фиктивный `bcrypt.compare`) —
  нельзя отличить «нет такого пользователя» от «неверный пароль» по таймингу.
- **Cookies**: `httpOnly: true`, `sameSite: "lax"`, `secure` в продакшене.
- **CSRF** на форме входа — встроенный double-submit токен NextAuth.

Проверено практически: `/admin/login` отвечает 401/редиректом, попытки входа
и блокировки пишутся в журнал.

**Осталось на усмотрение владельца:** 2FA. Поля `twoFactorSecret` и
`twoFactorEnabled` в схеме уже есть, TOTP-флоу не реализован — добавляется
без миграции БД.

## 2. Авторизация — ✅ закрыто

- Все `/admin/*` защищены в `src/proxy.ts` (Node.js runtime, поэтому может
  напрямую использовать `auth()` с Prisma).
- Дублирующая серверная проверка в `src/app/(admin)/admin/(dashboard)/layout.tsx` —
  UI не единственная защита.
- **Каждый** экспортируемый server action начинается с проверки сессии.
  Проверено скриптом: разобраны все `actions.ts`, действий без проверки — ноль.

Проверено практически: без сессии `/admin`, `/admin/artworks`, `/admin/orders`,
`/admin/messages`, `/admin/keywords` → 307 на страницу входа.

## 3. Валидация ввода — ✅ закрыто

- Все формы — серверная валидация **Zod** (`src/lib/validation.ts`).
- **Цене клиента не доверяем**: `/api/orders` пересчитывает сумму из БД.

Проверено практически: заявка, в которой клиент указал цену 1, сохранена
с настоящей ценой 690 000 ₩ — подмена не прошла.

- Заявка на проданную/зарезервированную работу отклоняется (409).
- Публикация работы заблокирована без alt-текста **на всех трёх языках**.

## 4. SQL-инъекции — ✅ не применимо (обосновано)

Везде Prisma с параметризованными запросами. `$queryRaw` / `$executeRaw` /
`$queryRawUnsafe` **не используются нигде** — проверено `grep` по `src/` и `prisma/`.
Строковой конкатенации в запросах нет по построению.

## 5. XSS — ✅ закрыто

`dangerouslySetInnerHTML` встречается ровно в двух местах, оба обоснованы:

1. **JSON-LD** — реализация в точности повторяет рекомендацию документации
   Next.js, включая экранирование `<` → `<`, которое сама документация
   называет мерой против XSS.
2. **HTML статьи блога** — санитизация **DOMPurify дважды**: при сохранении
   (`blog/actions.ts`) и повторно при рендере (`blog/[slug]/page.tsx`).

Проверено практически: вредоносный HTML (`<script>`, `<img onerror=>`,
`javascript:` в ссылке) записан **напрямую в БД в обход сохраняющего
санитайзера** — на отрендеренной странице не осталось ни одного из векторов,
уцелел только безопасный текст. Вторая линия защиты работает.

Весь остальной пользовательский текст экранируется React по умолчанию.

## 6. Загрузка файлов — ✅ закрыто

- **Проверка реального содержимого** через `sharp` (magic bytes), а не по
  расширению или заголовку `Content-Type`.
- Лимит размера — 10 МБ.
- Имена файлов — `crypto.randomUUID()`; имя, пришедшее от клиента, нигде не
  участвует в построении пути.
- Файлы лежат в `storage/uploads/` — **вне `public/`**, отдаются только через
  `/api/media/[filename]` со строгой маской `^[0-9a-f-]{36}-(full|thumb)\.webp$`
  и фиксированным `Content-Type: image/webp`.
- Эндпоинт требует сессию, ограничен по частоте и проверяет `Origin`.

Проверено практически (под сессией администратора):

| Файл | Результат |
|---|---|
| PHP-вебшелл с расширением `.jpg` и MIME `image/jpeg` | отклонён |
| GIF-полиглот со скриптом внутри | отклонён |
| SVG со встроенным `<script>` | отклонён |
| `text/plain` | отклонён |
| Настоящий PNG | принят, конвертирован в WebP |

Путь обхода каталога также проверен: `../../.env`, `..%2F..%2F.env`,
`....//....//.env` и вариант со склейкой валидного имени — во всех случаях
404/редирект, **содержимое `.env` не утекло ни по одному из путей**.

## 7. Заголовки безопасности и CSP — ✅ закрыто

Проверено практически на **production-сборке**:

```
content-security-policy: default-src 'self'; base-uri 'self'; form-action 'self';
  frame-ancestors 'none'; object-src 'none'; script-src 'self' 'unsafe-inline';
  style-src 'self' 'unsafe-inline'; img-src 'self' data: https:;
  font-src 'self' data:; connect-src 'self'; upgrade-insecure-requests
strict-transport-security: max-age=63072000; includeSubDomains; preload
x-frame-options: DENY
x-content-type-options: nosniff
referrer-policy: strict-origin-when-cross-origin
permissions-policy: camera=(), microphone=(), geolocation=()
```

`'unsafe-eval'` присутствует только в режиме разработки (нужен HMR) и в
продакшене отсутствует — проверено отдельно.

**Осознанный компромисс.** `script-src` содержит `'unsafe-inline'` вместо
nonce. Next.js App Router вставляет инлайн-скрипты для стриминга RSC
(`self.__next_f.push(...)`), которым нужен либо nonce, либо `'unsafe-inline'`.
Nonce требует чтения `headers()` в layout, а это переводит **все** страницы в
динамический рендеринг и убивает SSG/ISR — то есть ровно то, ради чего
проект и делается (скорость индексации). Выбран `'unsafe-inline'`, а
остаточный риск закрыт другими слоями: автоэкранирование React, двойной
DOMPurify на блоге, экранирование JSON-LD, отсутствие пользовательского
`eval`/`innerHTML` где-либо ещё.

## 8. Секреты — ✅ закрыто

- Все ключи в `.env`, файл в `.gitignore` (`.env*` с исключением `!.env.example`).
- `.env.example` содержит **все** обязательные переменные с пояснениями,
  включая `ENCRYPTION_KEY` (второй проход выявил, что он там отсутствовал —
  без него приложение не стартует, и деплой упал бы).
- Захардкоженных секретов в коде нет — проверено регулярным выражением по `src/` и `prisma/`.
- Проверено, что в `NEXT_PUBLIC_*` попадают только заведомо публичные значения

⚠️ **Важно про историю репозитория.** В коммитах, предшествующих этой работе,
в файле `.env` лежит рабочий токен Telegram-бота от прежнего проекта. Файл
удалён из отслеживания, но **остаётся в истории git**. Историю не переписывали:
это разрушительная операция, требующая явного решения владельца. Токен следует
считать скомпрометированным и отозвать.

## 9. Rate limiting — ✅ закрыто

| Эндпоинт | Лимит |
|---|---|
| Вход в админку | 10 / 10 мин / IP |
| `/api/contact` | 5 / 10 мин / IP |
| `/api/orders` | 5 / 10 мин / IP |
| `/api/admin/upload` | 30 / 10 мин / IP |

Плюс honeypot-поле `website` на формах контактов и заказа.

Проверено практически: 6-й заказ подряд получил 429; honeypot-заявка получила
ответ «успех», но в БД **не создана** (бот не понимает, что попал в ловушку).

`/api/media` намеренно без лимита: это отдача картинок с `immutable`-кэшем,
ограничение ломало бы загрузку страниц. Роут только на чтение, со строгой
маской имени.

**Ограничение:** лимитер хранит состояние в памяти процесса и на serverless с
несколькими инстансами не будет общим. Это best-effort защита от спама, не
строгая гарантия. Для строгой — бесплатный тариф Upstash Redis
(`@upstash/ratelimit`), интерфейс вызывающего кода менять не придётся.

## 10. Защита от мошеннических заказов — ✅ закрыто

`src/lib/fraud.ts` размечает заявки, **не блокируя** их: на сайте художника
ложное срабатывание (потерянный настоящий покупатель) дороже пропущенной
подозрительной заявки. Владелец видит оценку и причины в админке.

| Признак | Баллы |
|---|---|
| ≥5 заявок с одного IP за сутки | +40 |
| ≥3 заявок с одного IP за сутки | +15 |
| ≥3 заявок с одного email за сутки | +25 |
| Одноразовый почтовый домен | +30 |
| Имя без букв / слишком короткое | +20 |
| Аномально крупная сумма | +10 |

Проверено практически: заявка с `@mailinator.com` и именем «999» получила
score 50 с флагами `DISPOSABLE_EMAIL, SUSPICIOUS_NAME` и попала в журнал.
Контрольная проверка: заявка с корейским именем **김민준** получила score 0 —
проверка имени использует юникодный класс `\p{L}`, а не `[a-zA-Z]`, иначе
каждый корейский и русский покупатель помечался бы как мошенник.

## 13. Защита от утечек данных — ✅ закрыто

- **Минимизация**: у покупателя запрашиваются только имя, email, телефон и
  адрес — ничего сверх необходимого для отправки заказа.
- **Шифрование в БД**: имя, email, телефон, адрес и комментарий хранятся
  зашифрованными **AES-256-GCM** (`src/lib/crypto.ts`). Ключ — из
  `ENCRYPTION_KEY`; при его отсутствии приложение падает на старте, а не
  пишет данные открытым текстом (тихая деградация здесь опаснее сбоя).
- **IP не хранится в открытом виде** — только соль-хеш SHA-256, по которому
  адрес не восстановить. Тот же подход в журнале безопасности.
- **Поиск без расшифровки**: для антифрода и поиска повторов рядом лежат
  необратимые хеши email и IP.
- **Расшифровка только на сервере** под проверенной сессией. Проверено, что
  ни один клиентский компонент не импортирует `crypto`/`prisma`/`audit`/`fraud`.
- Разделение прав: роли `OWNER` / `EDITOR` в схеме; публичная часть к
  персональным данным доступа не имеет вовсе.

Проверено практически: сохранённая заявка в БД выглядит как
`4LZupe0KNZePGUX3:+C/I6JNbcu7...` — открытых имени и email в базе нет.

## 14. Логирование подозрительной активности — ✅ закрыто

Таблица `AuditLog`, запись через `src/lib/audit.ts`. Фиксируются:
`LOGIN_SUCCESS`, `LOGIN_FAILED`, `LOGIN_LOCKED`, `RATE_LIMIT`,
`SUSPICIOUS_ORDER`, `UPLOAD_REJECTED`, `CSRF_BLOCKED`.

Журнал виден в админке (**Аналитика** → «Журнал безопасности»), показываются
события уровня `warning` и `critical`. IP — в виде хеша: журнал не должен
становиться новым источником персональных данных. Сбой записи в журнал
никогда не роняет основной запрос.

Проверено практически: превышения лимита, успешный вход и рискованная заявка
появились в журнале с корректными уровнями.

## 15. Резервное копирование — ✅ закрыто (рекомендации)

Это операционная процедура, не код:

- **База данных.** Supabase и Neon дают автоматические point-in-time backups на
  платных тарифах. На бесплатном — `pg_dump` по расписанию (например, GitHub
  Actions cron) в объектное хранилище.
- **Ключ шифрования.** `ENCRYPTION_KEY` нужно хранить **отдельно от бэкапа
  базы**. Бэкап без ключа бесполезен: заказы не расшифровать. Копия ключа в
  менеджере паролей владельца — обязательна.
- **Медиа.** После перевода загрузок во внешнее S3-совместимое хранилище
  включите версионирование бакета — это и будет бэкапом. Локальная папка
  `storage/uploads` — только для разработки.
- **Код.** Репозиторий на GitHub при условии регулярных push.

## Что обязательно сделать при запуске

1. **Отозвать Telegram-токен**, оставшийся в истории git от прежнего проекта (см. п. 8).
2. **Сгенерировать `ENCRYPTION_KEY` и `AUTH_SECRET`** отдельно для продакшена
   (не переиспользовать локальные) и сохранить копию `ENCRYPTION_KEY` в надёжном месте.
3. **Сменить пароль администратора** после первого входа.
4. **Перевести загрузку изображений во внешнее хранилище** — на Vercel
   файловая система эфемерна, загруженные картины пропадут при следующем деплое.

## Второй проход: что он выявил

Первый проход прошёл по коду, второй — с попытками эксплуатации. Второй проход
нашёл три вещи, которые первый пропустил:

1. **`ENCRYPTION_KEY` отсутствовал в `.env.example`** — деплой упал бы при
   старте. Исправлено.
2. **Форма контактов писала в БД, но в админке не было страницы для чтения
   сообщений** — обращения покупателей уходили в никуда. Добавлен раздел
   «Сообщения» с расшифровкой и возможностью удаления (она же выполняет
   обещание из политики конфиденциальности удалить данные по запросу).
3. **Проверка имени в антифроде** изначально могла ложно срабатывать на
   нелатинских алфавитах. Переведена на юникодный `\p{L}` и проверена на
   корейском имени.
